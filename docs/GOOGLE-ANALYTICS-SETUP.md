# Google Analytics 4 setup

## Property

- Website: `https://www.technatonix.com/`
- Existing web stream: Technatonix, stream ID `16344867429`
- Measurement ID: `G-SW8R2C0VPT`

Use the existing property and stream. Do not add a second Google tag, GTM container, or GA integration in Vercel.

## Implementation

- `components/Analytics.tsx` loads the Google tag once after an explicit analytics choice or an approved regional default permits it. It tracks initial and client-side page views, disables analytics on admin routes, and captures annotated CTA clicks.
- `lib/analytics-consent.ts` contains the regional policy rules; `pages/api/analytics-consent.ts` resolves the policy using Vercel country and subdivision headers and returns a non-cacheable response.
- `lib/analytics.ts` centralizes the measurement ID, event names and URL filtering. Query strings are excluded except for safe UTM campaign values; fragments are omitted. The sanitized page context is also set globally for Google-generated events. Page titles are fixed and referrers are reduced to their origin on entry. Campaign values with unsupported characters or long digit sequences are discarded. Do not place names, emails, phone numbers or other personal information in URLs or UTMs.
- `pages/_app.tsx` mounts the integration on Pages Router pages.
- `pages/contact.tsx` records form interaction and success only after `/api/leads` returns a successful response. Product and automation conversions represent successful submissions from their respective enquiry links, not clicks. No form values or lead IDs are sent to GA.
- Visitors can accept or reject analytics and change that choice through the cookie policy. Rejecting disables the tag and removes accessible GA cookies. A browser that blocks local storage may need to ask again on a later visit.

No regional rules are currently enabled: analytics is denied by default for all visitors, including unknown locations, and visitors are prompted to accept or reject it. Visitors can also open preferences from the cookie policy. Existing explicit accept/reject choices remain in force. The Google tag is not loaded until analytics is allowed; when loaded it uses Consent Mode defaults denying `analytics_storage`, `ad_storage`, `ad_user_data`, and `ad_personalization`, with explicit acceptance updating only `analytics_storage`. This is basic consent mode, not a legal determination of consent requirements.

### Regional settings and legal approval

Before adding any rule to `regionalAnalyticsRules`, obtain documented legal approval for the specific country or subdivision, its analytics default and whether an automatic consent interface is required. Use uppercase ISO 3166-1 alpha-2 country codes or ISO 3166-2 codes such as `US-CA`; no examples are approved exceptions. A rule has `region`, `analyticsStorage` (`denied` or `granted`), and `prompt`. Denied regions requiring prior consent must have `prompt: true`; granted regions require an approved legal basis and appropriate opt-out controls. Advertising consent remains denied.

The region endpoint only trusts Vercel geolocation headers when running on Vercel. Missing or invalid locations and regions without a matching rule default to denied with a prompt. Where subdivision rules exist, a missing or unmatched subdivision also defaults to denied with a prompt rather than falling back to a country-wide grant. IP geolocation is approximate, and other hosting or proxies must not enable regional grants until their geolocation source and header integrity have been independently verified. Review the policy, interface and applicable laws with qualified privacy counsel and test the actual deployed Vercel behavior before enabling any rules. Regional grants must not be enabled until the GA4 privacy and duplicate-page-view issues below are resolved.

## Events

`page_view` is sent once on consent/initial page and for each completed client-side navigation. `send_page_view: false` is set globally before tag initialization and on the measurement configuration. `session_start` and `first_visit` are generated by GA4, not manually sent. Enhanced measurement can provide `scroll`, outbound `click`, `file_download`, `form_start`, and `form_submit` after the stream settings below are configured. These automatic form events are interaction signals, not evidence that the server saved a lead.

Custom events:

- `cta_click` with fixed button name, placement and optional service category.
- `ai_automation_cta_click` for the automation project CTA.
- `contact_form_start`, `contact_form_submit`, `contact_form_success`.
- `quote_form_start`, `quote_form_submit`, `quote_form_success`.
- `automation_project_enquiry`, `product_demo_request`, `product_enquiry` after a successful relevant enquiry.

Quote events apply to the quote entry point; other contact forms emit contact events. Product demo enquiries originate from the KREVIX demo link, and product enquiries from EFWRSX links. These classify the visitor's entry-point intent and do not guarantee lead qualification.

## Required Google Analytics configuration

These settings cannot be configured from the website code:

1. In **Admin → Data streams → Technatonix → Enhanced measurement**, enable the desired scroll, outbound click and file download measurements only after reviewing their payloads. Turn off **Form interactions**: testing showed Google's automatic `form_start` included the original form destination query string even with sanitized page context. Custom form and confirmed lead events remain available. Confirm the setting has propagated by inspecting actual network requests before deployment.
2. Under **Enhanced measurement → Page views → Advanced settings**, turn off **Page changes based on browser history events** for the Technatonix stream, then save. This prevents a second page view on client-side navigation while leaving the other enhanced measurement features enabled. The site sends initial and completed navigation page views itself. The current Google-hosted tag sent an additional page view on `history.pushState` in an isolated test with no manual page-view calls; its current dashboard setting has not been inspected. Do not deploy until the setting is verified and actual network requests confirm one sanitized page view per navigation.
3. In the web stream's **Redact data** settings, enable email and query-parameter redaction as appropriate. Audit outbound links, download URLs, form destinations, campaign parameters and GA event payloads for personal information; Google-generated enhanced measurement events can include link URLs and form metadata beyond the application's custom parameters. Never add form field values to analytics. Disable an enhanced measurement feature if its data cannot be made safe.
4. In **Admin → Events**, after each event appears, mark `contact_form_success`, `quote_form_success`, `automation_project_enquiry` and `product_demo_request` as key events. If they have not appeared yet, use **Admin → Key events → New key event**, enter each exact event name and save. Do not mark the corresponding click or submit-attempt events as key events.
5. Register `button_name`, `button_location`, and `service_category` as event-scoped custom dimensions if they are needed in standard reports. GA4 collects default traffic source attribution; use non-personal UTMs for campaigns.

## Verification

1. In a private browser, check that the analytics preference prompt appears and no request to `googletagmanager.com` or GA is made before consent or after rejection. Accept analytics and confirm that the tag request contains `G-SW8R2C0VPT`. Test changing the choice in the cookie policy, and test reviewed region rules and unknown locations before enabling them.
2. Use browser network tools and GA4 **Admin → DebugView** (with Tag Assistant or debug mode), plus **Reports → Realtime**, to verify one `page_view` for a direct load and one per client-side navigation. Disable enhanced browser-history page views first.
3. Inspect CTA events and test contact, quote, automation and product enquiry flows. A failed or rejected API response must not produce success/key events. Use mocked API responses in development to avoid creating real leads; verify a genuine success only with an authorized test lead.
4. Inspect outgoing GA requests for PII, including query strings, referrers and enhanced-measurement link/form metadata. Test withdrawal through the cookie policy and confirm GA requests stop.
5. DebugView and Realtime require access to the actual GA property and accepted consent. Browser requests alone do not prove that the property received or processed events.

## Maintenance

When adding CTAs, use fixed `data-analytics-cta`, `data-analytics-location`, and optional `data-analytics-category` attributes; never put user input in them. When adding forms, fire success events only after a confirmed backend success and document the intended conversion. Keep `send_page_view: false` and the GA enhanced-history setting in sync. Review consent, privacy settings and event payloads whenever tags, links or form flows change.
