# Technatonix Website — Requirements & Extraction Document

Last updated: 2025-09-23

Purpose
-------
This document captures the full, actionable requirements for the Technatonix marketing website and lead-capture system. The site is a Server-Side Rendered Next.js application. Firebase (Firestore + Storage) will be the primary data store for products, blog posts, case studies, and leads. The site serves both the product (KREVIX ERP) and service offerings.

Primary goals
-------------
- Showcase KREVIX ERP and its modules for manufacturers.
- Present software services and capture qualified project leads (RFPs).
- Serve product catalog, case studies, and blog content from Firebase.
- Provide a professional US-standard enterprise experience (SEO, accessibility, performance).

Pages and content model
-----------------------
Pages (SSR)
- Home
  - Hero: headline, subhead, 2 CTAs (Request Demo, Request Proposal)
  - KREVIX highlight section (summary, 3–4 benefits, screenshot)
  - Services grid (top 6 services)
  - Industries served carousel
  - Case studies preview
  - Client logos / trust band
  - Footer with local offices and legal links

- Services (list)
  - Service detail pages (slug-based)
  - Each service: problem, solution, outcomes, CTA

- Products (KREVIX ERP)
  - Product landing page with modules, feature matrix, screenshots, datasheet download, demo CTA

- Case Studies (list + detail)
  - Detail page: challenge, approach, result (metrics), tech stack, client quote

- Blog/Resources (list + article)
  - Paginated; articles stored in Firebase

- About
  - Company story, team, values, office locations, careers

- Contact & Demo
  - Two-step RFP form (short capture and detailed form)
  - Calendly or booking link

- Legal
  - Privacy Policy, Terms, Cookie Policy

Data sources
------------
- Firebase Firestore: primary store for dynamic content
  - Collections: products, services, caseStudies, posts, leads, settings
- Firebase Storage: product screenshots, case study images, lead attachments

Firebase data model (detailed)
- products (document per product)
  - id (string)
  - slug (string, unique)
  - title (string)
  - shortDescription (string)
  - longDescription (string, HTML or MD stored as HTML)
  - modules (array of {name, description})
  - screenshots (array of storage URLs)
  - datasheetUrl (string)
  - tags (array)
  - published (bool)
  - createdAt, updatedAt (timestamps)

- services
  - id, slug, title, description, offerings[], tags[], published, createdAt, updatedAt

- caseStudies
  - id, slug, title, clientName, problem, solution, results, techStack[], images[], clientLogoUrl, published

- posts
  - id, slug, title, excerpt, contentHtml, author, tags[], publishedAt, updatedAt

- leads
  - id (auto), name, email, company, country, phone, shortMessage, budgetBracket, timeframe, details (optional), attachments (array of storage URLs), source, utm, status, createdAt

- settings
  - siteTitle, contactEmail, phoneNumbers, socialLinks, gaMeasurementId, defaultLocale

API endpoints (Next.js server-side routes)
- POST /api/leads
  - Accepts form data (short or detailed) and optional file uploads
  - Validates reCAPTCHA token server-side
  - Writes lead doc to Firestore via Admin SDK
  - Uploads files to Firebase Storage (if provided) and stores URLs in lead doc
  - Sends webhook to CRM (HubSpot/Pipedrive) if configured
  - Returns 200 with lead id or error

- Optional helper endpoints
  - POST /api/verify-captcha — server-side verification helper
  - GET /api/settings — (optional) site settings for ISR/SSR caching

Security and rules
------------------
- Firestore rules
  - Public read allowed for collections with published==true (products, posts, caseStudies)
  - Deny direct client writes to `leads`; only server writes via Admin SDK allowed
  - settings collection read-only for public

- Firebase Storage
  - Use signed upload URLs generated by server for attachments
  - Restrict file types and size (max single file 10MB, total 25MB per lead)

- API security
  - Protect endpoints with server-side reCAPTCHA verification
  - Rate-limit by IP/address on server to mitigate spam
  - Store Firebase service account JSON securely in CI/CD environment variables

Lead capture and qualification flow
----------------------------------
- Step 1 (short): name, email, company, country, budget bracket, timeframe, short message
- Step 2 (detailed): optional follow-up form for qualified leads: number of users, integrations required, compliance (e.g., FDA), file upload, preferred contact times
- Qualification: flag leads with budget > threshold as high priority; route by country/industry
- Post-submit: autoresponder email with Calendly link + next steps

CRM integration
---------------
- Webhook payload: include lead doc fields and attachment URLs
- Support HubSpot (recommended) or Pipedrive by sending POST to their API with authentication

Localization & SEO
------------------
- Primary locale: en-US
- Secondary locales later: de-DE, en-UK, etc.
- Use hreflang headers for localized pages
- Provide localized metadata (title, description) stored per product/service if translations added

Analytics & tracking
--------------------
- GA4 measurement ID in `settings` and included SSR
- Add server-side event support for lead submissions (optional)
- Track UTM/source on lead docs

Accessibility & performance
---------------------------
- WCAG AA minimum
- Optimize images (use WebP/AVIF) and resize via build or Storage
- Use a CDN (Vercel/Cloudflare) and SSR caching patterns

Acceptance criteria
-------------------
- All pages render server-side with correct HTML and metadata.
- Products, posts, and case studies are served from Firebase and appear in SSR HTML.
- Submitting a short RFP stores a document in Firestore and returns a success response.
- Files uploaded via signed URLs are accessible only by link and saved to Storage.

3. Implement Firestore rules and test lead flow.
4. Scaffold Next.js SSR site (TypeScript + Tailwind) and wire to Firebase.
